# Claim queue: parallel art production

Many Codex agents generate world art at the same time (crowd, stage, NPCs, UI, VFX). This queue makes
sure **no two agents ever work on the same batch** and that every image lands under the right name.
Decision: [ADR 0008](../../docs/decisions/0008-world-art-and-parallel-production.md). Overview of the
areas: [../WORLD_ART.md](../WORLD_ART.md). Tool: `tools/queue.mjs` (Claude owns it).

There are two roles:

- **Workers** (many Codex sessions, named `w01`, `w02`, ...): claim a batch, generate its images, save
  them, mark it done, claim the next. They only ever write their own batch's output files.
- **The lead** (one Codex session, named `lead`): runs pilots, spawns workers, packs, builds contact
  sheets, queues reviews in `art/REVIEW.md`, records the user's decisions, re-opens rejected items and
  commits. Only the lead edits shared files.

If this page and the tool disagree, **the tool is the truth**: follow what it prints and the lead adds a
row for Claude in `docs/TASKS.md` so this page gets fixed.

## One working copy for everybody

Claims are files created with an exclusive create, which is atomic only **inside one folder on one
machine**. Every worker and the lead must run in the **same working copy** of the repo (local Codex
sub-agents or threads opened on this folder).

Agents that work in their own clone, worktree or cloud sandbox cannot see each other's claims. If you
must use them, the lead claims on their behalf in the shared copy (`npm run queue -- claim --agent w07`),
hands the printed batch to that agent, copies its finished images back to the printed paths and runs
`done` for it.

## Files

| file | what it is | written by | committed |
|---|---|---|---|
| `sources.json` | non-crowd batch sources: stage slots, NPCs (id + animations), UI images, VFX effects | lead or Claude, by hand | yes |
| `batches.json` | every batch with its items, prompt file and output paths; regenerated by `build` | the tool only | yes |
| `extra.json` | re-opened batches (`<batch>-rN`) created by `reopen` | the tool only | yes |
| `claims/<batch>.json` | one file per claimed batch: agent, status (`claimed` / `done`), times, items, note | the tool only | no (local coordination state; only `claims/.gitkeep` is committed) |
| `claims/_history/` | released and stale claims, moved aside | the tool only | no |
| `STATUS.md` | progress per type and the active claims; regenerated by `status` | the tool only | yes |

Crowd batches come from the rosters in `art/crowd/roster/<group>.json`, not from `sources.json`.
**Never edit `batches.json`, `extra.json` or anything in `claims/` by hand**, and never delete a claim
file: use the commands.

## Batches

A batch is the unit of work. Batch ids are stable as long as the sources do not change.

| type | batch id | items | prompt file (printed by `claim`) | output files (printed by `claim`) |
|---|---|---|---|---|
| `crowd` | `crowd-<group>-NN`, e.g. `crowd-dragon-ball-01`, `crowd-hunter-x-hunter-02` (`<group>` = the roster's `group`) | 10 spectators from one roster group, in roster order (the last batch of a group can be smaller) | `art/crowd/PROMPTS.md` + the roster file | `art/crowd/raw/<id>_vNN.png`, one image per spectator (3 poses in one row) |
| `stage` | `stage-<slot>`, e.g. `stage-grass` | 1 stage slot | `art/stage/PROMPTS.md`, brief `art/stage/ASSETS.md` | `art/stage/raw/<slot>_vNN.png` |
| `npc` | `npc-<id>`: `npc-announcer`, `npc-monk-a`, `npc-monk-b`, `npc-vendor` | the model sheet, then each animation | `art/npc/<id>/PROMPTS.md`, brief `art/npc/<id>/CHARACTER.md` | `art/npc/<id>/reference/model_sheet_vNN.png`, `art/npc/<id>/raw/<anim>_vNN.png` |
| `ui` | `ui-<name>`, e.g. `ui-logo` | 1 UI image | `art/ui/PROMPTS.md` | `art/ui/raw/<name>_vNN.png` |
| `vfx` | `vfx-<effect>`, e.g. `vfx-spark` | 1 effect strip | `art/vfx/PROMPTS.md`, brief `art/vfx/EFFECTS.md` | `art/vfx/raw/<effect>_vNN.png` |
| redo | `<batch>-rN`, e.g. `crowd-dragon-ball-01-r1` | only the re-opened items | same as the original batch, plus the lead's note | the next version of each re-opened item |

`claim` without `--type` hands out work in priority order: crowd, stage, npc, ui, vfx.

### Batch states

```
free --claim--> claimed --done--> done
                   |
                   +--release--> free            (the claim moves to claims/_history/)
                   +--3 h without done--> stale  (the next claim takes it over)

done batch with rejected items --lead: reopen--> new batch <batch>-rN (free)
```

A claim becomes **stale 3 hours after it was claimed** if it is not marked done; the next `claim` that
reaches it moves the old claim to `claims/_history/` and takes the batch. A batch of 10 spectators takes
far less than 3 hours, so a stale claim almost always means a crashed or stopped worker.

## Commands

Run them from the repo root (PowerShell or Git Bash). If `npm run queue` is not defined yet, use
`node tools/queue.mjs <command> ...` with the same arguments.

| command | who | what it does |
|---|---|---|
| `npm run queue -- build` | lead | regenerates `batches.json` from the rosters and `sources.json`; prints the batch count per type. Safe at any time: claims and `extra.json` are kept |
| `npm run queue -- claim --agent <name>` | worker | atomically claims the first free batch (crowd first) and prints the batch id, the items, the roster or brief, the prompt file and the **exact output paths** (next free versions) |
| `npm run queue -- claim --type crowd --agent <name>` | worker | same, limited to one type (`crowd`, `stage`, `npc`, `ui`, `vfx`) |
| `npm run queue -- done <batch> --agent <name> --note "..."` | worker | checks that every output of the batch has a current (non-rejected) `_vNN` file, then marks the batch done; `--note` is optional and is the way to report refusals, fallbacks and doubts to the lead |
| `npm run queue -- release <batch> --agent <name>` | worker | gives the batch back (for example when you have to stop) |
| `npm run queue -- reopen <batch> --items id1,id2 --note "..."` | lead only | creates the redo batch `<batch>-rN` with only those items (all items when `--items` is left out); the note tells the next worker what to fix |
| `npm run queue -- status` | lead | prints progress per type (done / claimed / stale / free) and the active claims, and writes `STATUS.md` |
| `npm run queue -- next-file <path-without-version>` | anyone | prints the next free versioned name, e.g. `art/crowd/raw/db-001` -> `art/crowd/raw/db-001_v02.png` (it counts `_rejected/` too) |

Example `claim` output:

```
BATCH crowd-dragon-ball-01  (crowd, 10 item(s))
roster: art/crowd/roster/dragon-ball.json  (read each item's entry there)
prompt: art/crowd/PROMPTS.md
save each image as the next free version (never overwrite):
  art/crowd/raw/db-001_v01.png
  art/crowd/raw/db-002_v01.png
  ...
when every item is saved: npm run queue -- done crowd-dragon-ball-01 --agent <you>
```

### Agent names

- Workers: `w01`, `w02`, ... `w12` (lowercase, two digits). The lead: `lead`.
- **Unique per running session**, and the same name in every command of that session. The tool cannot
  tell two sessions with the same name apart.
- A restarted worker may reuse its old name.

## Worker brief (the lead pastes this into each new worker)

Replace `<wNN>` with the worker's name, and add `--type <type>` to the claim if the lead wants that
worker on one area.

```
You are Codex art worker <wNN> for GCD Tourney, a browser HD-2D pixel-art anime fighter with a
Dragon Ball World Martial Arts Tournament stage. You work in the shared repo working copy (the path
contains a space: always quote it).

Read art/queue/README.md (sections "Worker loop", "Worker self-QA", "Workers never") and
art/WORLD_ART.md first. Then loop until `claim` prints "nothing left to claim":

1. npm run queue -- claim --agent <wNN>
2. Read the printed roster entries or brief and the printed prompt file (plus that area's README).
3. For each item, in order: build the paste-ready prompt from the prompt file and the item's entry,
   attach the area's approved style reference if the area README names one, generate the image with
   your built-in image generator, self-QA it (up to 3 attempts), and save the passing image to the
   exact path the claim printed.
4. npm run queue -- done <batch> --agent <wNN> --note "<refusals, fallbacks used, doubts>"
5. Claim the next batch right away. Do not wait for review.

Write only your batch's output files. Never edit shared files (art/REVIEW.md, art/TRACKER.md,
art/manifest.json, rosters, art/queue/*.json, art/queue/claims/), public/, src/, tools/, docs/ or root
files. Never run git add or git commit. Never overwrite or rename an existing _vNN file. If you must
stop, run: npm run queue -- release <batch> --agent <wNN>
```

## Worker loop

1. **Claim.** `npm run queue -- claim --agent <you>` (optionally `--type <type>`). Copy the printed block
   into your notes: batch id, items, roster or brief, prompt file, output paths. If it prints `nothing
   left to claim`, you are finished: tell the lead and stop.
2. **Read.** The prompt file and the area's README (crowd: `art/crowd/README.md`; stage:
   `art/stage/ASSETS.md`; NPC: `art/npc/README.md` and `art/npc/<id>/CHARACTER.md`; UI: `art/ui/README.md`; VFX:
   `art/vfx/README.md` and `EFFECTS.md`). For crowd batches, read each item's roster entry (`look`,
   `fallbackLook`, `heightClass`, `idle`, `cheer`, `shocked`, `tags`).
3. **Skip what already exists.** If an item of a normal batch already has a current `_vNN` file (not in
   `_rejected/`), a previous worker made it before releasing or going stale: self-QA that file; keep it
   if it passes, otherwise generate the next version. On a redo batch (`-rN`), if the rejected file is
   still in `raw/` and not in `_rejected/`, move it into the `_rejected/` folder next to it first (the
   batch note says so), then generate the next version.
4. **Generate each item.** Build the prompt from the template and the item's entry, exactly as the
   prompt file says, and attach the area's approved style reference if its README names one. NPC batches
   go in order: model sheet first, then each animation with the model sheet attached.
   Cameos: if the generator refuses or drifts off-model with the named prompt, switch to the item's
   `fallbackLook` and say so in your note.
5. **Self-QA** each image against the [checklist below](#worker-self-qa). Up to **3 attempts per item**.
   Failed attempts are not saved and use no version number.
6. **Save** the passing image to the **exact** path the claim printed (`<name>_vNN.png`). The image
   generator saves its output somewhere else: copy or move the PNG to that path, with exactly that name.
   If you are unsure about the number, `npm run queue -- next-file <path-without-version>` tells you.
7. **If an item still fails after 3 attempts**, save the best attempt anyway (so the batch can finish)
   and name it in your note, e.g. `db-007: shirt color drifts, needs a prompt fix`. If even the
   `fallbackLook` is refused, generate an original spectator with the same colors, build and props as the
   `fallbackLook` and note `db-007: refused, generated as original`.
8. **Done.** `npm run queue -- done <batch> --agent <you> --note "..."`. If it lists missing outputs,
   save them under the exact names and run `done` again.
9. **Claim the next batch** immediately. Never wait for review or for the lead.

## Worker self-QA

**Crowd** (every spectator image):

- [ ] One image, **three poses in one row in this order: idle, cheer, shocked**. Same spectator, same
      scale, feet on one baseline.
- [ ] Full body in every pose (hair or hat to feet), nothing cropped, clear gaps between the poses,
      nothing touches the canvas edge.
- [ ] **Flat #FF00FF background**, one color edge to edge, about 1536 x 1024. No floor, no ground
      shadow, no scenery, no frame or grid.
- [ ] **No text**: no letters, numbers, logos or watermarks. Signs, flags and clothes show simple shapes
      only.
- [ ] Front view facing the viewer, camera slightly above.
- [ ] Hard-edged pixel art, **1 px dark outline**, no blur, no gradients, no noise; about **24 colors or
      fewer**.
- [ ] **No magenta, hot pink or violet** inside the spectator (the packer deletes it). Pink hair or skin
      is a soft pastel or salmon pink.
- [ ] Matches the roster entry: every trait of the `look` (hair, outfit, colors, props) and the three
      pose lines. A cameo is recognizable from its traits alone.
- [ ] Proportions: adults have realistic anime proportions (spec v2, not chibi, not a big head); kids and
      creatures have natural proportions. The build fits the `heightClass` (a `huge` spectator is big and
      broad, a `tiny` one is a small kid or creature).
- [ ] `tall` and `huge` spectators cheer with arms **out to the sides**, not straight up.
- [ ] It looks clearly different from the other spectators in your batch (hair, colors, build).

**Stage, NPC, UI, VFX**: the QA list in the area brief (`art/stage/ASSETS.md`,
`art/npc/<id>/CHARACTER.md`, `art/ui/README.md`, `art/vfx/README.md`), plus the shared rules in
[../WORLD_ART.md](../WORLD_ART.md#rules-every-world-art-image-follows). In short: cut-out art on flat
#FF00FF, opaque textures and backgrounds fill the canvas (and tile seamlessly where the slot repeats),
hard pixels, no text, no ground shadow.

## Workers never

- edit shared files: `art/REVIEW.md`, `art/TRACKER.md`, `art/manifest.json`, `art/crowd/roster/*.json`,
  `art/queue/sources.json`, `batches.json`, `extra.json`, `STATUS.md`, anything in `art/queue/claims/`
  (other than through the commands);
- write outside their batch's output paths: no `public/`, `src/`, `tools/`, `docs/` or root files, and no
  other batch's images. **Stage exception:** a stage worker also writes the fit and tiling preview of its
  own saved raw, `art/stage/raw/_fit/<slot>_vNN.png` and `<slot>_vNN_2x2.png` (same version), as
  [art/stage/README.md](../stage/README.md#how-a-slot-flows) describes. Attempts are fitted and checked in a
  scratch folder outside the repo first, so failed attempts still never get a version;
- overwrite, rename or delete an existing `_vNN` file (the only move allowed is a rejected file into
  `_rejected/` on your own redo batch, as described in the worker loop);
- run `git add`, `git commit`, `git push`, `git stash`, `git checkout` or any other command that changes
  the repo state;
- run the packer or `npm run queue -- build` / `reopen` (lead only);
- hold more than one batch at a time.

## Lead loop

**Once, at the start**

1. `npm install`, then `npm run queue -- status` to check the tool runs.
2. Make sure `art/queue/sources.json` lists every stage slot (from `art/stage/ASSETS.md`), NPC and UI
   image (from `art/ui/README.md`), then `npm run queue -- build`. Re-run `build` whenever a roster or
   `sources.json` changes.
3. **Pilots.** Claim the first batch of each area as `lead` (or give each pilot to one worker with
   `--type`): `npm run queue -- claim --type crowd --agent lead`, the same for `stage` and `npc`.
   Generate, pack, queue them in `art/REVIEW.md` and ask the user to review the pilots together. When an
   area's pilot is approved, save the approved style reference the area README names (for example a
   few approved spectators), so every worker prompt can attach it.
4. **Spawn workers** with the [worker brief](#worker-brief-the-lead-pastes-this-into-each-new-worker),
   names `w01`... Start with about 4, grow to 8-12 once post-pilot batches pass review. Use `--type` to
   keep 1-2 workers on stage, NPC, UI and VFX. Do not spawn crowd workers before the crowd pilot is
   approved.

**Then repeat, every 15-30 minutes or whenever a worker reports a batch done**

5. `npm run queue -- status`. Look at the newly `done` batches and read each claim's `note` in
   `art/queue/claims/<batch>.json`.
6. **Pack**: `npm run sprites crowd` (atlas + contact sheets in `art/crowd/contact/`), `npm run sprites
   stage`, `npm run sprites npc`, `npm run sprites vfx`. UI images are cleaned by hand into
   `art/ui/final/` as `art/ui/README.md` describes. If a packer mode errors or does not exist yet, review
   the raw files directly and add a row for Claude in `docs/TASKS.md`.
7. **Lead QA.** Open each contact sheet or image. Reject obvious failures yourself (wrong pose count,
   text, magenta fringe, cropped feet, clearly off-model) with the
   [redo steps](#rejections-and-redo) before the user sees them.
8. **Queue the review.** Re-read `art/REVIEW.md`, then add one row per batch at the top: date, area
   (`crowd`, `stage`, `npc`, `ui`, `vfx`), batch id with its id range, link to the contact sheet or
   image, version(s), `needs review`, what changed, QA notes (worker notes included). Update
   `art/TRACKER.md` and `art/manifest.json` in the same edit.
9. **Commit** the batch ([commits](#commits-lead-only)).
10. **Ping the user** with the list of batches waiting (every five batches or every hour, not after each
    one), with the contact sheet paths.
11. **Record decisions** as they arrive: approved -> rows, TRACKER and manifest; redo or reject -> the
    [redo steps](#rejections-and-redo). Commit.
12. **Fix sources** from worker notes: a refused or drifting cameo gets a better `look` or `fallbackLook`
    in its roster (lead only), then `reopen` that item.
13. **Keep the queue full.** When free batches drop below about 2 per worker, add roster groups or slots
    (or ask Claude or the user for them) and run `build`. Workers must never idle.
14. **Watch for stale claims** in `STATUS.md`. A stale claim is taken over automatically by the next
    `claim`; restart or replace the worker that held it.
15. **Engine and packer problems** go to Claude as a row in `docs/TASKS.md` (owner Claude, the batch or
    file, the exact error line). Do not edit `tools/` or `src/`. The lead does not commit `docs/` or root
    files; Claude commits them, including the `CHANGELOG.md` line when it integrates an asset type.

### Rules for changing sources

- **Append, never reorder or delete.** Batches are cut from roster order, 10 at a time. Inserting,
  reordering or removing a spectator shifts the items of every later batch in that group, including
  batches that are claimed or done. New spectators go at the **end** of a group or into a **new group
  file**. A spectator that should not be used is handled in review (rejected or excluded in the
  manifest), not deleted from the roster.
- Ids are unique across all roster files (`build` warns about duplicates and skips them) and never
  change once a batch with them exists.
- A group's `group` value never changes: it is part of every batch id cut from it.

## Rejections and redo

Only the lead does this, after the user's decision or the lead's own QA:

1. Move each rejected file into the `_rejected/` folder next to it (`art/crowd/raw/_rejected/`,
   `art/stage/raw/_rejected/` (with the raw's `_fit/` files), `art/npc/<id>/raw/_rejected/` (model sheets:
   `art/npc/<id>/reference/_rejected/`), `art/ui/raw/_rejected/`, `art/vfx/raw/_rejected/`). The version
   number stays used; the next attempt gets a higher one. A rejected NPC model sheet usually means its
   animation strips are redone too: reopen the whole NPC batch.
2. Update the `REVIEW.md` row: for a partial redo the row becomes `approved` with `redo: db-003, db-007
   (reasons) -> crowd-dragon-ball-01-r1` in QA notes; for a whole-batch reject the row becomes
   `rejected` with the reason. Fix the file links.
3. `npm run queue -- reopen crowd-dragon-ball-01 --items db-003,db-007 --note "db-003: hair must reach
   the shoulders; db-007: adult proportions, not chibi"`. Leave out `--items` to reopen the whole batch.
   This creates `crowd-dragon-ball-01-r1` (then `-r2`, ...), which the next worker claims like any other
   batch.
4. If the reason is a roster or prompt problem, fix the roster entry or ask for a prompt fix first, so
   the redo does not repeat it.
5. When the redo comes back, it gets its own `REVIEW.md` row.

## Stale claims, crashes and interruptions

- **A worker has to stop**: `npm run queue -- release <batch> --agent <name>`. Images already saved stay;
  whoever claims the batch next keeps the ones that pass QA (worker loop step 3).
- **A worker crashed**: its claim turns stale after 3 hours and the next `claim` takes the batch over.
  The lead can restart the worker under the same name; it simply claims a new batch.
- **`done` says the batch is claimed by another agent**: your claim went stale and was taken over. Stop
  working on it, keep the files you saved (versions are never reused) and claim a new batch.
- Nobody deletes or edits claim files to "unstick" a batch.

## Commits (lead only)

- Commit only `art/**` and `public/{crowd,stage,npc,ui,vfx,characters}/**`, always with **explicit
  paths**. Never `git add -A`, `git add .` or `git commit -a`.
- Add a batch's own files by name (the claim file lists its items), plus the shared files you changed.
  A whole folder is fine only where no worker writes (`public/crowd/`, `art/crowd/contact/`). This keeps
  other workers' half-finished batches out of the commit.
- Commit `art/queue/batches.json`, `extra.json`, `sources.json` and `STATUS.md`; never `art/queue/claims/`
  (only its `.gitkeep`).
- Conventional messages: `art(crowd): add crowd-dragon-ball-01 v01 (10 spectators)`,
  `art(crowd): redo db-003, db-007 (crowd-dragon-ball-01-r1)`, `art(stage): add grass v01`,
  `art(npc): approve announcer v02`, `art(vfx): add spark v01`.
- If git reports that `index.lock` exists, another session (usually Claude) is committing: wait about
  10 seconds and retry, up to 5 times. Never delete the lock file while a git process is running.

Example:

```
git add -- art/crowd/raw/db-001_v01.png art/crowd/raw/db-002_v01.png ... art/crowd/raw/db-010_v01.png \
  art/crowd/contact/crowd-dragon-ball-01.png public/crowd/atlas.png public/crowd/atlas.json \
  art/REVIEW.md art/TRACKER.md art/manifest.json art/queue/STATUS.md
git commit -m "art(crowd): add crowd-dragon-ball-01 v01 (10 spectators)"
```

## Troubleshooting

| you see | meaning | do |
|---|---|---|
| `nothing left to claim` | every batch (of that type) is claimed or done | worker: tell the lead and stop. Lead: add sources and `build` |
| `no batches: run npm run queue -- build first` | `batches.json` is missing | lead: `npm run queue -- build` |
| `<batch> is claimed by w05, not w03` | someone else holds the batch (your claim went stale) | stop on that batch, keep your files, claim a new one |
| `<batch>: missing output(s)` | some items have no current `_vNN` file | save them under the exact names listed, then `done` again |
| `<batch> is already done` | it was finished already | claim a new batch |
| `warn: <file>: duplicate or missing id` during `build` | two roster entries share an id, or one has none | lead: fix the roster (ids unique across all groups), `build` again |
| `npm ERR! Missing script: "queue"` | the npm script is not wired yet | use `node tools/queue.mjs <command> ...` |
| `npm run sprites crowd` fails or does not know the mode | the packer world mode is missing or broken | lead: review raw files directly, add a row for Claude in `docs/TASKS.md` |
| the generator refuses a cameo name | content policy on the name | use the entry's `fallbackLook`; note it in `done --note` |
| the background comes out as a gradient or off-magenta | generator drift | regenerate (counts as an attempt); restate "one flat #FF00FF background, edge to edge" |
| a saved file has the wrong name (no `_vNN`, a typo) | saving mistake | rename your own unsubmitted file to the printed name before `done`; never rename someone else's file |
